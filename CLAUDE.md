# Alias Maker

A beginner-friendly terminal app (GTK 4 + VTE window) plus the `doit` command, for CachyOS with fish. Python 3, no third-party packages beyond PyGObject/VTE.

Current goal: the author calls the project feature complete for now (1.1.0); it's in testing on a real Steam Deck. Fix what breaks and keep adding documentation links; don't add features unasked. Known rough edges: /clippy shows translated Arch Wiki pages for one-word searches, and very short searches match loosely.

## Layout
- `src/aliasmaker_core.py`: the engine (custom commands, fish shortcut file, Database scan/search, /clippy, logging, settings). Both the window and `doit` use it.
- `src/aliasmaker`: the GTK 4/VTE window and its ☰ menu.
- `src/doit`: thin launcher for the engine.
- `src/shell/lets-do-stuff.fish`: prompt, title, welcome and /clippy inside the window.
- `packaging/`: installer `.run` builder and Arch PKGBUILD.
- `docs/DESIGN.md`: full design and status. Read only the sections the task needs.

## Commands
- Tests: `python3 -m unittest discover -s tests` (fish tests skip if fish isn't installed)
- Try the engine safely: `src/doit --dry-run <phrase>`

## Status
- The engine is tested. The window runs on Ubuntu 24.04 (GTK 4.14, VTE 0.76, fish 3.7 and 4.9.3) under Xvfb, and the AppImage on a clean Ubuntu chroot, and the author has run the standard AppImage on a real Steam Deck (SteamOS) and says it works as intended (daily use still to come); nothing has been tried on CachyOS or other PCs yet. To test the window from source in a sandbox: `apt-get install gir1.2-gtk-4.0 gir1.2-vte-3.91 fish xdotool`, run it with `python3.12` (the system PyGObject) under `xvfb-run`, and screenshot with `import -window root`.
- Releases: bump `VERSION` in `src/aliasmaker_core.py`; on `main`, `.github/workflows/release.yml` tests, builds and publishes the installer, pacman package, AppImages (app + Debug) and the AUR/Flathub hand-off kits. Don't commit built files.
- `.github/workflows/debug-build.yml` (manual): builds the AppImages from any ref into a private DRAFT release (`debug-<sha>`) so the user can virus-scan them first; it replaces older `debug-*` drafts only and never touches real releases.
- The author won't publish on the AUR or Flathub (doesn't want to deal with their moderation). Don't set up publishing there; keep `packaging/handoff/` usable by volunteer packagers instead.
- The AppImages are self-contained (`packaging/appimage/make-bundle.sh`, built on Ubuntu 24.04; needs glibc 2.38+): Python, PyGObject, GTK 4, VTE, the MIME database and Adwaita symbolic icons. No shell is bundled. Libraries are found through a relative RUNPATH (patchelf), not LD_LIBRARY_PATH. `AppRun` has no dialogs and no dependency checks by design (the user wants a clean start: no pop-ups, no extra installs, few processes). `AppRun` remembers what it changes as `ALIASMAKER_ORIG_*` / `ALIASMAKER_WAS_UNSET_*` and the window hands the shell back the originals (`crash.child_env_fixes`; VTE merges the env you pass instead of replacing it, so removal is done with `env -u`). From an AppImage, one-word fish commands call `$APPIMAGE doit` (`doit_command()`), since the AppImage's own folder vanishes when it closes. 
- Graphics: `crash.use_opengl_not_vulkan()` runs before GTK loads (GSK_RENDERER=ngl, Vulkan off) because on a Steam Deck in desktop mode Valve's Gamescope Vulkan layer pops up a zenity "Gamescope WSI Layer Error" for GTK 4's Vulkan renderer.
- Testing the AppImage on a clean system: debootstrap an Ubuntu 24.04 minbase chroot with only X11/Mesa/fontconfig libs (no python, GTK, fish, mime db), bind /dev, /dev/pts and /tmp/.X11-unix, run `Xvfb :99`, run the AppImage with `APPIMAGE_EXTRACT_AND_RUN=1`, drive it with xdotool and screenshot with `import`. Find the window with `xdotool search --pid`, and stop test processes with `pkill -x` (never `pkill -f` with a name that is also in your own command line).
- The user now tests on a Steam Deck with stock SteamOS (bash login shell, read-only root), not CachyOS.
- Shell rule (the user was explicit): Alias Maker runs whatever shell the PC uses (`core.login_shell()`: ALIASMAKER_SHELL, the account's shell, $SHELL) and only *paints* `Let'sdostuff~` over the prompt and title. Never swap the user's shell for another one. fish: `src/shell/lets-do-stuff.fish`; bash: `src/shell/lets-do-stuff.bash` (started with `bash --rcfile`, sources /etc/bash.bashrc and ~/.bashrc first, then paints the prompt through PROMPT_COMMAND, turns `/clippy` into `doit clippy` on Enter via a readline binding only when Enter is plain accept-line, handles `command_not_found_handle`, and loads `~/.config/alias-maker/shortcuts.bash`). `/clippy` is its own slash-command lookup helper, separate from the prompt. Other shells start unchanged (welcome only). `tests/test_shell.py` runs the bash script in a real bash on a pty.
- /clippy follows the detected OS (the user asked for it: never point an Ubuntu user at CachyOS docs): `data/docs.json` maps `os` IDs (first match wins; specific before family) to sources of kind sitemap / mediawiki / search / link / stackexchange, each optionally with a `home`; `default` is used when a system has no entry. `/clippy` is a not-AI search helper: vague asks get "What do you need help with?", Enter opens a generated results page (`clippy-results.html`, everything escaped, http(s) links only) in the browser, and stackexchange sources are searched only after the user says yes once (`clippy_web` setting, `doit clippy web on|off`). No entry means "I don't have a documentation source for X yet" and manual pages only. Only user-supplied or verified URLs go in the list; most doc sites are unreachable from the sandbox, so test the mechanism with the stand-in servers and say so. The user is gathering more documentation links (Debian, Fedora, SteamOS/Valve and others) to add.
- Saved commands are checked before running (`check_programs_exist()`): a missing program is explained, and this OS's example with the same phrase is offered (swapped only on a yes). Per-system examples live in `data/examples.json` (`os`, `not_os`, `needs`); keep a family's example from catching a derivative with its own packages (Manjaro is not Arch for keyrings).
- Typo helper (`typo_suggestions()`, `offer_typo_fix()` in `explain_not_found()`, reached through the shells' command-not-found hooks): up to 3 close programs from the live PATH plus one-word custom commands, ranked by typo distance; runs one only when its number is typed, full command shown first, risky programs (`RISKY_PROGRAMS`) ask again, nothing is asked when stdin isn't a terminal. `os_translation()` / `offer_translation()` handle another Linux's package commands (apt, pacman, dnf, yum, zypper) and old names (ifconfig, netstat): this PC's version is offered by number, package names are plain words only and run as an argument list (never through a shell, except Alias Maker's own update command), changes ask for a yes, SteamOS never gets pacman installs, and `sudo apt ...` can't be caught (sudo reports it before any shell hook). As-you-type ghost text isn't built: fish has its own autosuggestions; bash has none without ble.sh, which would replace its line editor, so ask the user before adding it.
- AI helper (`ai_*` in the core, `AIWindow` in the window, `/ai` in both shell scripts): optional, off by default, no network until the user adds a key, switches it on and chats. Hard rules from the user: the AI can't see files or run commands (plain chat, never add tools, never run or paste its output anywhere but the screen, and `plain_reply()` strips terminal codes), only the key is asked for (never a username or password), and the chat must always look different from the terminal (title, banner, `AI chat ❯` prompt, bar on AI lines, "just text" marks, `looks_like_command()` guard), and it must stay light (standard library only, no SDK, no background process, nothing saved from chats). "Other service" (provider `custom`) takes a user-typed https address (http only for localhost), never a guess, and the first-chat notice says the key and messages go there. `/swapai` only applies model names found in the service's own list, orders free first, and says free/paid/price-not-listed strictly from that list (never guess a price or call something free). The author has confirmed a real chat works against Token Reply (https://api.tokenreply.com/v1) on a Steam Deck. Anthropic and xAI endpoints are written from their documented formats and have only been tested against stand-in servers, so say so; model names come from the service's own list, not from code.
- Flatpak: `packaging/handoff/flathub/PORTING.md` lists the code changes (`flatpak-spawn --host` for the shell, the scan and doit). Update its line numbers if those functions move.
- Cross-OS: `detect_os()` reads `/etc/os-release`; the scan uses pacman or dpkg (`package_tool()`); examples carry `os`/`not_os`/`needs` and only fitting ones are offered; the window rescans when a PATH folder's mtime changes (`library_outdated()`). No rpm support yet. With a login shell that is neither bash nor fish (e.g. zsh) there's no Let'sdostuff~ prompt, /clippy or one-word commands.
- Known gaps: commands run through `sh` (`subprocess.run(..., shell=True)`), not fish, so fish aliases/syntax fail; the forced "ask first" check only looks for the word `sudo` (misses `doas`, `pkexec`, `run0`, `&&sudo`).

## Rules
- Never delete or change the real program a command points to; deleting only edits `~/.config/alias-maker/custom.json`.
- Never write a shortcut that hides a real program, fish built-in or CachyOS alias.
- Always show the real command before running it, and never run an unknown phrase on a guess.
- Keep user-facing text in plain words for someone new to Linux.
- Update the Status table in `docs/DESIGN.md` when something gets built or tested.
